# 项目选题说明：为什么做恶意 WiFi 检测？

## 一句话概述
**帮助普通用户在公共场所一键识别 WiFi 安全风险，避免个人信息被窃取。**

---

## 1. 问题背景：WiFi 便利背后的安全隐患

### 1.1 场景触达
走进咖啡厅、机场、商场，打开手机 WiFi 列表，眼前可能出现一排相似的热点名称。对普通用户来说，很难判断哪个是官方 WiFi，哪个是伪装成官方 WiFi 的"蜜罐"。

### 1.2 攻击成本极低
- 一台几十元的 ESP8266 芯片就能搭建一个伪装热点
- 手机热点功能随手可开，改个 SSID 就能模仿星巴克免费 WiFi
- 不需要任何编程能力，淘宝买成品设备即插即用

### 1.3 后果严重
- DNS 劫持 → 银行页面被重定向到钓鱼网站
- 中间人攻击 → 聊天记录、密码明文传输被截获
- Portal 认证伪造 → 手机号 + 验证码被收集贩卖

**一句话：连错一个 WiFi，个人信息可能全部暴露。**

---

## 2. 现有方案的局限

| 方案 | 问题 |
|------|------|
| 杀毒软件 / 手机管家 | 只查病毒，不分析 WiFi 安全性 |
| VPN | 能加密流量，但用户得先连上 WiFi 才知道需要 VPN |
| WiFi 分析类 App | 需要 root 权限、抓包能力，普通用户门槛极高 |
| 安全科普文章 | 看了记不住，实际连 WiFi 时还是凭直觉选 |

**核心矛盾：最需要保护的人（非技术背景的普通用户），却接触不到最有效的判断工具。**

---

## 3. 我们的切入思路

### 3.1 降低决策门槛
不是告诉用户一堆协议名词（WPA2/WPA3/EAP），而是用一个**红/黄/绿灯**的直观界面，让任何人都能在一秒内做出安全决策。

### 3.2 模拟安全专家的判断逻辑
安全专家看到一个 WiFi 会问 3 个问题：
1. 有没有加密？什么级别的加密？
2. DNS 有没有被劫持的迹象？
3. 有没有奇怪的 Portal 认证跳转？

我们用规则引擎把这种思维模式固化成代码，用户点击一下就能获得类似安全专家的诊断结果。

### 3.3 MVP 优先，边用边改
与其做一个功能大而全但半年出不来的产品，不如先用最小可行版本跑通核心流程，拿给真实用户测试，收集反馈后再迭代。

---

## 4. 目标用户画像

| 用户类型 | 典型场景 | 核心诉求 |
|----------|---------|---------|
| 大学生 | 图书馆、咖啡厅自习 | 快速判断公共 WiFi 是否可信 |
| 出差/旅行者 | 机场、高铁站、酒店 | 在陌生环境识别欺诈热点 |
| 非技术背景的上班族 | 商场、餐厅 | 不懂安全术语，需要直观的"安全/危险"指示 |

---

## 5. 项目定位与边界

### 5.1 我们做的是什么
- 一个**辅助决策工具**：告诉用户某个 WiFi 风险有多高，为什么
- 一个**安全意识入口**：通过直观的可视化，让用户意识到 WiFi 安全风险的存在
- 一个**课程演示项目**：展示"AI Agent + 规则引擎"在安全领域的应用思路

### 5.2 我们不做的是什么
- 不是杀毒软件（不管设备上的病毒）
- 不是防火墙（不拦截实际网络流量）
- 不是真实的网络监控工具（所有数据为模拟演示）

### 5.3 为什么选择 Python + Streamlit
- Streamlit 可以把一个数据分析脚本在几分钟内变成可交互的 Web 应用
- Python 的规则引擎写法直观，适合课程演示和迭代
- 整个 MVP 可以用不到 500 行代码跑通完整业务流程

---

## 6. 长远想象空间

如果这个 MVP 继续演进，可以走向的方向：

- **真实数据接入**：对接 WLAN API 或驱动层获取真实 WiFi 列表
- **云端威胁情报**：接入已知恶意 SSID/Hotspot 黑名单数据库
- **大模型增强**：用 LLM 替代固定规则的意图分析，输出更自然的诊断报告
- **社区共建**：用户反馈数据汇聚形成众包威胁情报

---

> **一句话总结这个项目的价值：让每个普通人都能像安全专家一样判断 WiFi 是否安全。**
